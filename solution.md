# Scraper-сервіс для збору app-ads.txt — архітектурне рішення

## 1. Розрахунок навантаження (визначає всю архітектуру)

Перш ніж обирати компоненти, рахуємо реальний обсяг роботи.

**Вхідне припущення:** в умові вказано «десятки мільйонів Bundle ID», тобто діапазон 10–99M. Далі беру **30M** як робочу середину. Усі числа нижче лінійно масштабуються від цього значення — при 10M це 17 RPS, при 90M — 150 RPS. Точна цифра змінює sizing пулів, але не архітектуру.

**Weekly — перевірка сторінок у сторах.** Масштабується за кількістю застосунків:

```
30M Bundle ID / 7 днів / 86 400 с ≈ 50 RPS сталого навантаження
```

**Daily — завантаження app-ads.txt.** Масштабується за кількістю **унікальних доменів**, а не застосунків. Один видавець має десятки застосунків, але один сайт:

```
30M застосунків → ~0.5–1M унікальних registrable-доменів
1M / 86 400 с ≈ 12 RPS
```

Різниця в 4–5 разів. Тому дедуплікація за доменом закладається в схему даних, а не додається як оптимізація пізніше.

**Третє спостереження:** у App Store живих застосунків ~1.8M, у Google Play ~2.5M. «Десятки мільйонів Bundle ID» означає, що база містить історичні, видалені та неперевірені ID — значна частина ніколи не зарезолвиться. Звідси експоненційний backoff для «мертвих» ID замість щотижневого довбання 404. Це знижує реальне навантаження weekly-пайплайну приблизно втричі.

**Висновок:** вузьке місце — це не мережа й не БД, а **anti-bot сторів**. Архітектура будується навколо економії запитів до App Store / Google Play.

## 2. Модель даних

Ключове рішення — розділення `apps` і `domains`:

| Таблиця | Призначення | Ключові поля |
|---|---|---|
| `apps` | Один рядок на Bundle ID | `bundle_id`, `store`, `developer_id`, `status`, `next_check_at`, `fail_streak` |
| `developers` | Видавець у сторі | `store_developer_id`, `name`, `website_url`, `domain_id` |
| `domains` | **Одиниця роботи daily-пайплайну** | `host` (точний хост із discovery — ціль запиту), `registrable_domain` (eTLD+1 — тільки для групування й резолву `SUBDOMAIN`), `origin` (`discovered` / `subdomain_referral`), `etag`, `last_modified`, `content_hash`, `next_check_at`, `state` |
| `adstxt_snapshots` | Версії файлу | `domain_id`, `content_hash`, `fetched_at`, `s3_key` |
| `adstxt_records` | Розпарсені рядки | `domain_id`, `ad_system`, `publisher_id`, `relationship`, `valid_from`, `valid_to` |

**Ціль запиту — точний хост із discovery, а не eTLD+1.** Схлопувати `games.example.com` і `news.example.com` в `example.com` не можна: піддомени можуть мати власні файли й власні дані про власність, і при схлопуванні ми або втратимо їх, або підставимо одному застосунку файл іншого. PSL потрібен, але для іншого — для групування, коректного резолву делегації `SUBDOMAIN=` і нормалізації, а не для заміни цілі запиту. Дедуплікація від цього не страждає: більшість URL видавців вказують на кореневий домен або `www`, тож кількість унікальних хостів лишається того ж порядку. Точний порядок обходу (корінь → делегація vs прямий запит на хост) звіряємо з чинною версією специфікації IAB на фазі 2 — модель із двома колонками коректна за будь-якого прочитання.

`valid_from` / `valid_to` замість перезапису дають історію змін власника й вмісту файлу — це прямо потрібно для weekly-вимоги «виявлення зміни власника».

Сирі файли — в S3 (дешево, незмінно, можна перепарсити при зміні логіки). Метадані й стан — у PostgreSQL. Розпарсені записи — в PostgreSQL з партиціонуванням; якщо обсяг перевищить ~500M рядків, виносимо в ClickHouse.

## 3. Компоненти

Окремого брокера черг немає — чергою є сама таблиця: «протерміновані» це просто рядки з `next_check_at <= now()`.

```
        ┌─────────────────────── PostgreSQL ───────────────────────┐
        │                                                          │
        │   apps  (weekly)                  domains  (daily)       │
        │   next_check_at                   next_check_at          │
        └────────┬─────────────────────────────────┬───────────────┘
                 │                                 │
      claim: WHERE next_check_at <= now()  FOR UPDATE SKIP LOCKED
                 │                                 │
                 ▼                                 ▼
      ┌────────────────────┐            ┌────────────────────┐
      │ Discovery Workers  │            │   Fetch Workers    │
      │ ─ iTunes Lookup    │            │ ─ HTTP + ETag      │
      │ ─ Play HTML        │            │ ─ валідація типу   │
      │ ─ headless (рідко) │            │ ─ стрім-парсер     │
      │ ─ через проксі     │            │ ─ без проксі       │
      └─────────┬──────────┘            └─────────┬──────────┘
                │                                 │
                │  новий / змінений хост:         │  зміна content_hash:
                │  INSERT INTO domains            │  S3 + snapshots + records
                │  next_check_at = now()          │
                └────────────────►────────────────┘
                                  │
                                  ▼
                    Change Events → зовнішні споживачі
```

Стрілка знизу — **єдиний зв'язок між пайплайнами**: discovery пише прямо у вхід fetch. Один INSERT, без проміжного шару.

**Два незалежні пайплайни.** Discovery і Fetching мають різні throughput, різні режими відмов і різну ціну запиту. Спільний пул воркерів означає, що блокування Google Play зупинить і збір app-ads.txt.

**Планувальник — не cron, а due-based.** Тригером є не час, а стан рядка: кожен запис несе колонку `next_check_at`, і claimer раз на 10 секунд забирає ті, у яких цей час уже настав (`next_check_at <= now()`, `LIMIT N`, `FOR UPDATE SKIP LOCKED`). Після обробки воркер планує себе сам: `next_check_at = now() + 24h + random()`.

Що це дає порівняно з cron, який о 00:00 ставить у чергу мільйон задач:
- **Плоский профіль.** Інтервал відлічується від моменту завершення, тому записи самі розмазуються по добі й такими лишаються. Розклад не будується — він виникає.
- **Немає стану поза БД.** Падіння воркера чи деплой не потребують надолуження пропущеного запуску — після підйому claimer просто знову питає, що протерміноване.
- **Один механізм на всі інтервали.** Daily (`+24h`), weekly (`+7d`), backoff для мертвих ID (`+2^fail_streak днів`), адаптивна частота — це одна й та сама логіка з різними значеннями.
- **Вимірюваний backpressure.** Метрика «вік найстарішого протермінованого запису» прямо відповідає на питання, чи встигаємо в SLA.

**Черга.** На старті — таблиця в PostgreSQL із `SKIP LOCKED`. На 50 RPS цього вистачає з великим запасом, і це на один компонент менше в експлуатації. Виносимо в окремий брокер лише коли з'явиться друга система-споживач подій.

## 4. Ключові технічні рішення

**Ескалація за ціною запиту.** iOS — офіційний `itunes.apple.com/lookup?bundleId=`, HTML не потрібен. Android — сторінка Play server-rendered, дані видавця вже в першій відповіді (`AF_initDataCallback`), тож вистачає HTTP GET. Headless виправданий рівно в одному випадку: прийшов `200`, це не consent-сторінка, але блоку з даними немає. Решта відмов лікується дешевше — `429` ротацією проксі (браузер з того самого забаненого IP дасть той самий бан, лише в 50 разів дорожче), consent-редирект куками, відсутнє поле при наявному блоці це drift парсера й алерт. Частка headless обмежена квотою, вихід на квоту — алерт, а не автоскейлінг.

**Conditional GET — несуча конструкція daily.** `ETag`/`Last-Modified` → `If-None-Match`/`If-Modified-Since`; файли змінюються рідко, тож 90%+ відповідей мають бути `304`. Факт зміни визначаємо за `sha256`, снапшот пишемо лише при новому хеші.

**Стани замість помилок.** Відсутність файлу — валідний факт, а не збій: `OK` / `NO_FILE` / `NOT_APPLICABLE` (URL веде на Facebook чи linktree) / `BLOCKED` / `ERROR`. Змішування отруює метрики й ховає реальні блокування. Сюди ж три пастки коректності: **Public Suffix List** потрібен для коректного eTLD+1 (`split('.')` ламається на `games.example.co.uk`) — але для групування й делегації, а не для підміни цілі запиту; **soft-404** ловимо перевіркою `Content-Type: text/plain` і структури перших рядків; директиви `SUBDOMAIN` / `OWNERDOMAIN` / `MANAGERDOMAIN` зі специфікації IAB вимагають рекурсивного обходу (з обмеженням глибини й захистом від циклів) і потрібні для валідації власності.

**Проксі — тільки для discovery.** Fetch ходить на звичайні сайти видавців, і це 95% запитів; платні проксі там помножили б рахунок без причини. Стан пулу в Redis (`healthy` → `degraded` → `cooling` → `dead`). Бан тимчасовий — cooldown з експонентою, а не викидання IP. Token bucket на кожен IP окремо, бо стор лімітує IP, а не хост. **Circuit breaker на рівні пулу**: якщо в `cooling` одночасно більше X%, це зміна політики стору — зупиняємось і алертимо, інакше спалимо весь пул за 15 хвилин.

**Таймаути роздільні, лізинг довший за них.** Один загальний таймаут — помилка: 2 с відсічуть повільний дрібний хостинг, і ми запишемо «немає app-ads.txt» там, де він є. Розкладка: connect 5 с / TLS 5 с / TTFB 10 с (через проксі вдвічі), стеля 60 с. Для великих файлів працює **таймаут простою** (немає байтів 15 с), бо він відрізняє «повільно, але качається» від «зависло». Звідси вимога коректності: `locked_until > total_timeout × attempts`, тобто лізинг 5 хвилин — коротший дає подвійну обробку.

**Конкурентність задає латентність, не RPS** (`L = λ × W`), причому середню латентність визначає хвіст: 50 RPS × 4.8 с ≈ 240 одночасних з'єднань. На цьому масштабі впираємось не в CPU, а в DNS (1M різних доменів — окреме навантаження на резолвер, потрібен локальний кеш), file descriptors і ephemeral-порти.

**Відмови — даними, а не окремою чергою ретраїв.** Невдача це інше значення `next_check_at`: блип і `5xx` — 2–3 спроби в пам'яті воркера, далі `fail_streak++` і backoff зі стелею ~90 днів; `429` не ретраїться взагалі. Окремий `attempt_count` у межах циклу ловить **poison-записи** → `QUARANTINED` плюс алерт, інакше файл із багом парсера вічно кладе воркерів. `last_check_at` і `last_successful_check_at` — різні колонки, інакше споживачі не відрізнять «нічого немає» від «п'ять днів не достукались».

**Оркестратор не потрібен.** Airflow/Temporal вирішують багатокрокові процеси з залежностями, а тут одна однорідна незалежна задача, повторена 4M разів на добу — граф плаский. Ретраї, розклад і backfill уже виражені однією колонкою (backfill — це `UPDATE ... SET next_check_at = now() WHERE ...`). Переглянути варто, якщо потік стане сагою з компенсаціями.

**Інфраструктура:** PostgreSQL — стан і черга, Redis — ліміти й стан проксі, S3 — сирі файли, Kubernetes з HPA за глибиною черги. Per-host token bucket захищає сайт видавця, у якого 200 застосунків у базі.

## 5. Вибір мови: Node.js чи Go

Навантаження неоднорідне, тому оцінюємо мови окремо по двох пайплайнах.

| Критерій | Go | Node.js |
|---|---|---|
| Конкурентні з'єднання | Горутина ~4 KB стеку → десятки тисяч на інстанс | Event loop тримає багато сокетів, але пам'яті на з'єднання більше |
| CPU-bound парсинг (10 MB файли, sha256) | Справжня паралельність по ядрах «з коробки» | Блокує event loop → потрібні `worker_threads` або більше процесів |
| Стрімінговий парсинг | `bufio.Scanner` по body — константна пам'ять | Streams вміють те саме, ергономіка гірша |
| Headless-браузер | `chromedp` — робочий, але помітно сиріший | **Playwright/Puppeteer — референсна реалізація**, екосистема stealth-плагінів |
| Парсинг Play HTML | Потрібен окремий обхід вкладеного JS-об'єкта | `AF_initDataCallback` — це буквально JS; парситься природно |
| Деплой | Статичний бінарник ~20 MB, старт <100 мс → швидкий HPA | Образ із `node_modules`, старт повільніший |
| Типізація парсерів | Компілятор ловить drift-помилки до продакшну | TypeScript закриває, але не на рівні рантайму |

### Переваги Go

Fetch-пайплайн — це десятки тисяч одночасних HTTP-з'єднань плюс sha256 і рядковий парсинг файлів до 10 MB. Це рівно та комбінація IO + CPU, де Go виграє двічі: горутини дають дешеву конкурентність, а планувальник розкидає парсинг по всіх ядрах без окремих процесів. Стрімінговий `bufio.Scanner` тримає константну пам'ять незалежно від розміру файлу. Статичний бінарник і старт за десятки мілісекунд роблять автоскейлінг за глибиною черги реально швидким. `golang.org/x/net/publicsuffix` — канонічна реалізація PSL.

### Переваги Node.js

Discovery-пайплайн — це anti-bot. Playwright у Node — референсна реалізація (Go-порт завжди відстає), і вся екосистема обходу детекції написана під Node. Дані видавця в Google Play лежать у `AF_initDataCallback` — це JS-структура, і витягати її з JS природніше, ніж писати обхід на Go. `undici` дає HTTP-клієнт, конкурентний з `net/http`. Плюс швидша розробка парсерів, які й так доведеться часто переписувати через drift.

### Рекомендація

Архітектура вже розділена на два незалежні пайплайни — це дозволяє розділити й мови по межі, яка існує незалежно від них:

- **Fetch Workers (daily, app-ads.txt) → Go.** І завантаження, і парсинг — end-to-end.
- **Discovery, дешевий рівень (iTunes API, простий HTTP до Play) → Go.** Теж end-to-end.
- **Discovery, headless-рівень (~5% запитів) → Node + Playwright.** Ізольований сервіс за HTTP-інтерфейсом: приймає Bundle ID, повертає готовий JSON із даними видавця.

**Межа проходить по пайплайнах, а не по стадіях обробки.** Поділ «Go завантажує, Node парсить» був би помилкою: довелося б ганяти тіла файлів між процесами, це зруйнувало б стрімінговий парсинг (файл довелося б повністю буферизувати перед передачею) і віддало б Node саме ту CPU-bound роботу, яка блокує його event loop. Критерій межі — **домен відмови**: бан у сторі й недоступність сайту видавця це незалежні події, а «завантажив/розпарсив» усередині одного пайплайну — ні.

Чесне застереження: два стеки — це подвійна експлуатація, CI та onboarding. Якщо команда невелика, беремо **одну** мову, яку команда знає краще, і виносимо headless окремим сервісом на Node — він ізольований за визначенням, тож це не «другий стек», а спеціалізований компонент. Якщо стартувати з нуля без обмежень по команді — Go для ядра, бо основний обсяг роботи (95% запитів) припадає на fetch-пайплайн, де він об'єктивно сильніший.

**Якщо Node-only** — на цьому масштабі повністю робочий варіант за трьох умов. Перша: `undici` замість глобального `fetch`, бо потрібні роздільні таймаути (`connect` / `headersTimeout` / `bodyTimeout`, де останній і є таймаутом простою). Друга: парсинг **стрімом по чанках** — кожен чанк це окремий тік, тож event loop не блокується на 500 мс, як було б при розборі 10 MB файлу цілком; декодувати обов'язково через `StringDecoder`, бо наївний `chunk.toString()` ламає багатобайтові символи на межі чанків, а `sha256` рахувати по сирих байтах до декодування. Третя: масштабування процесами плюс pgbouncer, бо N процесів × власний пул з'єднань упреться в `max_connections` Postgres. `worker_threads` при стрімінговому парсингу зазвичай не потрібні. Go виграв би при десятикратному зростанні; на поточному масштабі це питання команди, а не техніки.

## 6. План імплементації

| Фаза | Обсяг | Результат |
|---|---|---|
| **1. MVP** (~1 тиж) | Схема даних, iTunes Lookup, fetcher з валідацією, парсер app-ads.txt | Наскрізний потік на 10k Bundle ID, ручний запуск |
| **2. Повнота даних** (~1–1.5 тиж) | Google Play парсер, PSL-нормалізація, `SUBDOMAIN`, стани й версіонування | Обидва стори, коректна класифікація станів |
| **3. Масштабування** (~1.5 тиж) | Due-based scheduler, rate limiting, проксі-пул, retry з backoff, headless-фолбек | Стабільні 50 RPS, повна база |
| **4. Експлуатація** (~1 тиж) | Метрики, алерти на drift парсерів, tiering проксі, потік подій змін | Продакшн-готовність |

**Економія без порушення розкладу** (фаза 4). Вимога «щодня» лишається контрактом: усі живі домени перевіряються раз на добу, інтервал не розтягується. Економія береться з **здешевлення кожної перевірки**, а не з пропуску днів — conditional GET уже дає це безкоштовно, бо 90%+ відповідей це `304` з порожнім тілом, тобто денний цикл коштує на порядок менше за наївний. Легітимно виключаються тільки сутності, яких не існує: `APP_REMOVED`, `NOT_APPLICABLE` і мертві ID, де backoff застосовується до неіснуючого об'єкта, а не до живого видавця. Розтягування інтервалу для «стабільних» доменів **не закладаємо**: воно суперечить ТЗ і псує саме той випадок, який нібито оптимізує — файл може простояти застарілим тиждень. Якщо навантаження виявиться проблемою, зміна частоти виноситься замовнику як окреме рішення, а не приймається на рівні дизайну.

## 7. Ризики й компроміси

**Крихкість парсера Google Play.** Розмітка змінюється без попередження. Мітигація: версіоновані парсери + алерт на різке падіння success rate (падіння з 95% до 20% — це drift, а не масове видалення застосунків), збереження сирого HTML для проблемних відповідей.

**Вартість проксі — головний драйвер бюджету, і модель тарифікації важливіша за прайс.** Обсяг: 4.29M запитів/добу × ~100 KB gzip ≈ 430 GB/добу. Звідси residential з оплатою за трафік ($3–8/GB) одразу відпадає — $40–100k/місяць. Оренда виділених IP — теж дорого й надлишково. Робочий варіант — **rotating datacenter subscription**: тарифікація за кількістю потоків, не за трафіком чи IP. Кількість потоків рахуємо за тією ж латентністю, що й решту системи: `L = λ × W` при `W ≈ 2–4.8 с` (з урахуванням хвоста й таймаутів) дає **100–240 одночасних сесій**, а не 25 — оптимістичні 0.5 с тут дали б план, який заріже discovery нижче цільових 50 RPS. Такий обсяг усе ще вміщується в типові плани (зазвичай 100–1000 потоків), але це вже старший тариф: порядок — від сотень доларів на місяць, і точна цифра залежить від виміряного розподілу латентності через конкретного провайдера.

**Метрика для порівняння — вартість одного успішного завантаження**, `cost_per_request / success_rate`, а не ціна за IP чи за гігабайт. Це не формальність: у спільних пулах репутація IP спільна, а скрейпінг Play — один із найпоширеніших сценаріїв на ринку проксі, тож ті самі адреси вже «прогріті» іншими клієнтами провайдера. Втричі дешевший пул із утричі гіршим success rate не дає жодної економії, зате додає ретраї, латентність і розмазує розклад.

**Рівні проксі дзеркалять пріоритет даних, не частоту.** Оскільки розклад фіксований ТЗ, диференціюємо не інтервал, а вартість спроби: масовий потік іде через дешевий shared-пул, а виділені IP тримаємо для топ-N застосунків і для **ескалації після невдачі** — перша спроба дешева, ретрай дорожчий. При добовому вікні на ретраї помірний success rate дешевого пулу прийнятний, бо невдала спроба переплановується в межах тієї ж доби. Це та сама драбина ескалації за ціною, що застосована до headless.

Вибір провайдера не робиться за прайс-листом: тріальні плани у 2–3 провайдерів, однакова вибірка 10k Bundle ID, порівняння cost-per-success. Задача фази 3. Усі цифри тут — ринкові порядки, не котирування.

**Anti-bot і ToS.** Скрейпінг Google Play формально порушує умови використання. Мітигація: пріоритет офіційних API, дотримання robots.txt, агресивне кешування, backoff на 429. Альтернатива для обговорення — комерційні data providers для Android-частини.

**Обсяг `adstxt_records`.** ~1M доменів × 200–5000 рядків = мільярди записів при повній історії. Компроміс на старті: зберігаємо повну історію снапшотів у S3, але в реляційній БД тримаємо тільки актуальну версію розпарсених рядків + діфи. Повна історія відновлюється зі снапшотів за потреби.

## Припущення, які потребують уточнення

1. Чи потрібна історія значень `app-ads.txt`, чи достатньо поточного стану + факту зміни? Це визначає, чи знадобиться ClickHouse.

3. Чи потрібні дані per-storefront (різні країни), чи достатньо однієї локалі (`gl=us&hl=en`)?
